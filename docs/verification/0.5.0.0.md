**CI failure found and fixed (run 38089382489, the first CI run of the 3D tests):** on the GitHub runner's software WebGL, every Playwright action took 5–17 s once the model was showing, and 7 showcase tests timed out. The stage drew at 30 fps whatever a frame cost, and drew synchronously on every drag or key event. The fix, MPES §10.3 and `source/showcase/pace.ts`: a drawn frame is timed by the gap to the next animation frame, the next draw waits at least twice that (1 s at most), and every redraw goes through that one paced frame. Locally the failure did not reproduce, even with SwiftShader pinned to one core, so the runner is the oracle for this fix.

**Second CI run red (run 38097185474, commit `043fba9`): two root causes, read from the downloaded traces** (`gh run download 38097185474 -D .artifacts/ci-38097185474`):

1. *Firefox, Node 24, three showcase tests* (`showcase.spec.ts` lines 37, 82, 155): the trace console reads "Failed to create WebGL context: AllowWebgl2:false restricts context creation on this system". Firefox refuses WebGL on that GPU-less runner, so the page correctly showed the stills and the 3D tests waited for a mode that could not come. Fix: `playwright.config.ts` launches Firefox with `webgl.force-enabled`, giving it a software context as Chromium has. No oracle or timeout changed; the stills fallback keeps its own tests.
2. *Perf, Node 22* (stills, no WebGL): showcase update 245 ms (budget 100), angle change 108 ms (50), turntable step 122 ms (50). Each update built new `<img>` elements, so every unchanged layer was decoded again, and the warmed turntable frames were separate images the page never used. Decoding runs off the main thread, so 4× (and even 12×) CPU throttling here did not reproduce it (12×: 132 / 38 / 24 ms). Fix (MPES 4.1.1 §10.3 "Still decoding"): `DecodedImages` in `source/showcase/showcase.ts` keeps decoded images and reuses them (24 at most, never one on screen); when the page is idle the other angle, the turntable and the frames either side are decoded ahead, and `#showcase[data-prepared]` reports it. Node 24 perf was skipped because its browser projects failed.

**Third CI run red (run 38106258905, commit `aca9d45`, docs only): an intermittent turntable spike on Node 24.** Perf, Node 24: turntable step 665 ms (budget 50); update 67 ms, angle change 25 ms, 3D ready 2,602 ms, all within budget. Node 22 passed (turntable step 19 ms). The trace (`gh run download 38106258905 -D .artifacts/ci-38106258905`) shows the first two steps after the turntable opened taking about 410 and 720 ms, and the next four fast. Root cause: the frames either side were prepared in `requestIdleCallback` (500 ms timeout), and on the busy runner no idle time came within the 300 ms pause, so the first steps decoded their frames on demand. Locally idle time comes at once, so the fault showed only on CI; the test now reproduces it by making idle callbacks wait for their timeout. Fix (MPES 4.1.2 §10.3): preparation starts as soon as the shown view has decoded, never on idle; the images exist at once, so a step never creates one; an angle view also prepares the turntable frames either side of the entry frame; while turning, the frames ahead in the direction of travel come first. No budget, pause or wait changed. Version 5.0.0-dev.1.
