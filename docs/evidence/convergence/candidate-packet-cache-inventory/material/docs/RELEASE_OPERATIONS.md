# SEA Game release and operations — candidate procedure

This procedure is prepared for R19/R20/R23/R25/R26 and T20/T21/T24/T26/T27. It is not owner acceptance, a published release or an installed autonomous service. Current HEAD remains baseline 1b80b348ac945987fbe11db77bd7a51f3dd553aa; local modifications are an uncommitted candidate. Follow [MPES](MPES.md) and [ledger](EXECUTION_LEDGER.md) for current gate status. Rights, content/classroom, supported browser/device/accessibility, candidate CI, independent review and operational handover remain OPEN.

## Prepare and retain a candidate packet

From the project root, run `node tools/build.mjs --check`, `node tools/test.mjs`, `node tools/test-journey.mjs`, `node tools/test-package.mjs`, `node tools/test-mpes.mjs` and `node tools/check-mpes.mjs`. Preserve each actual environment/result and the image audit separately. The delivered journey suite remains command/persistence VM evidence, not actual browser acceptance. Candidate CI must execute against the actual integrated candidate revision; local Windows/WSL runs cannot substitute for its four Windows/Ubuntu Node22/24 jobs.

Run `node tools/package.mjs --output docs/evidence/convergence/NEW_PACKET_NAME` with a new directory name. The tool refuses existing output, checks source/build parity and specification contracts, copies each keyed material file without changing its bytes, and writes packet.json. Material includes both standalone HTMLs, optional assets, source, tools, documentation, reference/controlled evidence and workflow/configuration inputs. Run-record/convergence directories are excluded to avoid recursively packaging previous packets. Retain the printed key independently with the verification evidence, outside the packet.

Run `node tools/package.mjs --verify PACKET_DIRECTORY EXPECTED_KEY`. Verification requires that external key and rejects changed bytes, rewritten inventory, missing/extra members, path escape and symlinks. A self-consistent edited packet is insufficient. Integrity hashes are not signatures or rights/acceptance evidence. The tool always labels packets UNQUALIFIED_CANDIDATE and records zero full closure passes; its key covers package bytes only, not the complete PRODUCT_RELEASE evidence identity.

The packet's material directory is the reconstructible local candidate tree. From that directory run `node tools/build.mjs --check` and `node tools/test.mjs`; compare standalone SHA256 hashes with packet.json. Keep the retained original packet unchanged. A packet containing source is an engineering snapshot, not a permission to redistribute its inherited artwork or code.

## Qualify, freeze and release

Before classroom distribution, attach actual decisions for learning goals, six missions/scoring/deck/balance, art/code permissions and classroom fitness; complete every applicable R/T and M0-M8 gate. Record named reviewers, scope, candidate identity, date and actual decisions. Self-review remains self-review. Rehearse both roles through all eight phases and 70 lots, EN/FR, supported devices/browsers, file/offline/storage/art failure, keyboard/touch/zoom/assistive use and performance. Follow [recovery guide](RECOVERY_GUIDE.md) and [security review](SECURITY_REVIEW.md).

Freeze a PRODUCT_RELEASE identity binding exact committed source/generated bytes, assets/rules/deck/save schema, tests/fixtures, actual OS/browser/device/build versions, workflow/action/dependency provenance, actual candidate CI, rights/content/classroom decisions, operating documents, acceptance and deployment evidence. The local specification fingerprint and package key do not replace this identity. Run three fresh, distinct full-closure adversarial reviews at that same identity, with zero changes and zero new material findings. Any material change or invalidated evidence resets the identity and sequence.

Publication requires verified current authority and accepted gates. Preserve the previously accepted packet and deployment identity first. Do not assume the currently hosted baseline is accepted or rollback-compatible merely because it runs. Use the repository's established workflow under the verified grant; record operation intent, expected revision and returned run/deployment identity. If the effect is unknown, inspect that same run/deployment before repeating. Read back both delivered HTMLs and optional asset bytes and compare SHA256 to the approved packet; freshly download/reopen both roles and complete smoke/recovery checks. A HTTP200 or successful workflow alone is insufficient. A mismatch leaves activation incomplete and triggers reconciliation/rollback under authority.

## Classroom activation and handover

Use the [EN/FR classroom quick start](CLASSROOM_QUICK_START.md) for facilitator/student rehearsal. Its candidate instructions require actual language, device and classroom acceptance before activation.

The facilitator receives the exact accepted instructor HTML, student HTML, optional same-folder assets, verified hashes, support contact and accepted support envelope. Demonstrate opening both roles offline, language switching, private planning/manual handoffs, projection-safe submissions, authoritative ledger, result interpretation, export/re-import and next-session reset. Record the actual facilitator/operator rehearsal and readiness decision; do not invent a contact or acceptance.

Use synthetic information. Instructor backups contain private market and class records; student backups contain that team's private work. Keep the roles and files separate. Before scored play, after each round and before any device/tab/version handoff, request exports and verify completed saved files. Never close a tab or replace a session based solely on a download request. Only the instructor ledger is authoritative; student data is manually reconciled.

## Rollback and recovery rehearsal

Retain the previous accepted version intact, with its exact packet key, schema/rules/deck identity, compatible synthetic fixtures, approval and deployment receipt. If no accepted predecessor exists, record that limitation and rehearse stopping/restoring the candidate; never label the unaccepted baseline as an approved rollback version.

Before changing a classroom version: pause bidding, record the authoritative lot/leader/time and ledger manually, export both roles and verify saved files. Test copies of these backups in the retained version using its matching role, schema/rules/deck validator; unsupported versions stay unchanged. Do not edit/downgrade live files, overwrite old backups, or assume a newer appVersion implies compatibility. An open instructor auction must recover paused with accepted bids retained and private-entry projection disabled.

In a disposable local rehearsal copy, verify the retained packet against its external key, restore its exact material tree, reproduce standalone bytes and run its relevant tests. Then perform actual supported-browser import, ledger/position/notes comparison and resume/close checks. Record candidate/predecessor keys, original/copy backup hashes, environment, commands and observed outcomes. Local byte restoration covers only the package step; it cannot close browser/session migration or deployed rollback gates.

For a deployed rollback, act only under the recorded rollback grant and accepted compatibility evidence; read back deployed bytes and repeat download/open/recovery checks. If no compatible rollback is proven, stop dependent play and retain the current tab, files and manual ledger while support reconciles state. Do not silently resume a guessed version.

## Support and improvement

On lost/incorrect transaction, invalid save, rendering/injection/CSP fault or unusable control, pause the affected activity and preserve private exports/rescue bytes and the instructor manual ledger. Collect version/packet identity, phase/lot, synthetic reproduction, environment, storage/file route, expected versus observed result and error text. Do not put real plans, classroom private files, market seed/order or sensitive information in public issues/logs. Preserve original evidence in a private authorized location; obtain only the minimum diagnostic data needed.

Reproduce against the exact version; derive the relevant R/T acceptance examples; produce a meaningful failing behavior test; repair the smallest cause, run affected and full package/browser gates, and requalify a new identity. Actual incidents/changes trigger this cycle. There is no installed scheduler or monitor in this candidate; a future recurring run needs an authorized real runtime and verified invocation. No change is automatically a release.

## Deprecation and retirement

An actual owner decision and current authority trigger deprecation/retirement. Identify scope, dates, successor, private state export, retention obligations, support window and archive destination. Warn affected operators through an explicitly authorized channel; this document does not authorize sending messages. Rehearse synthetic exports/restoration and successor compatibility first.

After the agreed handover/retention conditions are met, execute only the granted disabling/removal action and verify its real postcondition. Archive the accepted packet, approvals, hashes, recovery/retention record and final support status in the authorized location. Delete private files only under explicit retention/disposal authority, with required verification. Unresolved obligations keep retirement open. An ended agent turn, stopped process or dormant lifecycle row is not retirement. Initial release requires this executable procedure and actual rehearsal; it does not require shutting the product down immediately.
