## Executive assessment

SEA Game has a substantial playable implementation and a working publication pipeline. It is not yet a verified, maintainable, classroom-ready completion of the intended recreation. The highest-value next work is to fix a demonstrated reconciliation defect, make builds reproducible on Windows, lock down rules and recovery behavior, and test actual classroom journeys before further redesign.

No defensible overall completion percentage can be inferred from source volume or successful CI. Feature presence, correctness, browser compatibility, educational acceptance, and operational readiness are separate measures. The [MPES](MPES.md) defines a finite release scope and evidence-based completion gates.

This assessment created documentation and audit evidence only. Product files were not changed, and nothing was committed, pushed or deployed by this assessment. Historical instructions to implement/push are treated as project history; the present task is analysis and specification.

## Architecture and implementation maturity

The deliverables are two independent single-file HTML applications. Development inputs are split into two HTML templates, shared CSS, a very small shared engine, and two large role scripts. The engine contains constants, reveal visibility and win eligibility. Most financial arithmetic, card definitions, scoring, persistence validation, localization, artwork and rendering still reside in the role scripts, with significant duplication. Each controller is approximately 0.8 MB in this Windows checkout, including large inline artwork; byte size must not be confused with executable logic complexity.

The build uses only Node built-ins. It checks template slots, parses assembled JavaScript, rejects native browser dialogs and compares generated bytes. Existing tests are useful safeguards but include source-string assertions that cannot catch event-handler defects. CI currently has a Linux source-parity job and a path-filtered artwork validation workflow. It does not establish Windows reproducibility, a browser support matrix, recovery correctness, accessibility or educational fitness.

The pure-rule extraction is a foundation rather than a completed recreation. A low-risk path is to capture original semantics as independent fixtures, extract deterministic rules/data behind explicit interfaces, then revise role workflows in increments. A simultaneous full rewrite would discard useful behavior before sufficient equivalence tests exist. Retain the two-file distribution and zero-runtime-dependency model.

## Post-assessment candidate evidence

This is a cents-versus-dollars conversion error, not a change to the canonical card price. The local candidate now uses the existing cents-to-dollar formatter before parsing the sale value; a red/green rendered-handler regression checks the unchanged displayed price against exact canonical cents across all 70 cards. Windows Node 24 and Ubuntu WSL Node 22 test/build checks pass for that candidate. Neither local fix is deployed or browser-qualified.

The deployed removal click still reproduces `ReferenceError: i is not defined` and leaves the displayed purchase and totals unchanged. The built-in browser's `file:` navigation was denied by its URL policy, which permits only HTTP(S) and forbids reaching the local page through another route; the hosted smoke test is evidence about the published baseline, not the local candidate. Full T10 browser acceptance remains open.

The current local candidate also implements the first M4 recovery slice: separate version-1 instructor/student backup envelopes bind role, app, ruleset, deck, schema and session identity; import checks file size before reading and delegates to the existing schema-3 role validator. It rejects cross-role, newer-schema and unknown-field data, requests a role-labelled export of the active session before confirmed replacement, and rechecks the captured state so stale confirmation cannot overwrite intervening work. A validated prior session can be restored in-app through the same confirmation and validation path. Tests exercise both role validators and replacement handlers, including storage-write failure and oversized files. This is partial code evidence only: browser file/download behavior, corrupt-storage rescue, multiple tabs, compatible rollback and full recovery journeys remain open.

The candidate now requires every open auction to be revealed and, for a closed current auction, requires leader/price to match the effective SALE or be cleared when no SALE is active. Direct validator and role-specific import checks exercise rejection while retaining valid SALE/UNSOLD states. Windows/WSL tests and regenerated standalone byte parity pass; this remains local recovery evidence, not browser acceptance.

## Important requirements distinctions

- Previous-round reveal history already exists in `renderMarket`; the old handover's claim that it is missing is stale. Current-round visibility derives from mode/current position, and history derives from completed rounds. Prove monotonic visibility under all allowed transitions before adding a new persistent reveal-history mechanism. If the proof fails, add a migrated representation rather than guessing prior visibility.
- The student does not receive the instructor's randomized market order: it enters announced card IDs manually. Both public HTMLs contain card definitions. This is a classroom authority model, not secret-data security or tamper-proof anti-cheat.
- The student planning value `maxWtpCents` defaults to 85,000,000 cents ($850,000). It is not an enforced aggregate team spending cap in the inspected rules. Do not invent a hard budget constraint from general handover wording or the QA showroom's dummy budget.
- Existing award logic ranks submitted, compliant, positive-score teams by exact bid/score ratio; this is distinct from merely sorting highest score. Shared first-place ties and no-award outcomes need explicit tests.
- `qa.html` labels its showroom as simulated. Those specimens, manual checkboxes and HTTP checks cannot certify production gameplay. It also retains rounded styles; decide whether to restyle this auxiliary surface under the recorded sharp-edge visual constraint.
- Session storage is a convenience rather than a durable backup; the candidate's manual downloads provide a recovery path but are not browser-qualified. `file://` behavior must be measured in supported browsers; localStorage would not remove that portability requirement. [MDN storage guidance](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage).

## Recommended execution

Follow [MPES milestones M0-M8](MPES.md#milestones-and-execution-order). Begin with the two confirmed defects and regression tests, then capture full rule/content contracts and extract shared logic. Recovery and instructor authority are more important than cosmetic rework. Refine the unified UI using real phase journeys; finish with browser/offline/accessibility coverage and classroom acceptance. Publication already works, so replace generic deployment setup work with release verification and rollback exercises.

No product readiness, WCAG conformance, balance approval or Omni ASSURED convergence is claimed by this analysis.
