# MPES assurance review contract

Version 1, 2026-10-08. Controlling target: SPECIFICATION under [MPES 1.1.1](../MPES.md), not product release or an installed autonomous service. This file fixes the review scope/method before the three confirmation passes. It is itself a keyed evaluator input.

## Material closure and identity

Include MPES, XY analysis, dated project analysis, live execution ledger, README, reference provenance/originals/governance, frozen rule and baseline/currentness evidence, synthetic scenarios, checker and mutation-test source; validate current source/templates/styles/build/tests/workflows/assets/launcher/QA as material implementation dependencies. The key includes every tracked repository file, untracked non-ignored files and all controlled files in `source`, `assets`, `.github`, `docs` and `tools`, including ignored files in those material roots. Symlink dependencies require explicit qualification rather than silent traversal.

Bind Git HEAD plus actual working bytes, Node/OS/Git environment, reviewer capability mode and currentness basis. Refresh live main and deployed-byte observations before freeze and check for material remote change before final reuse. Do not treat a local hash as proof of fresh remote state. Web sources are dated evidence with explicit reopening triggers; unavailable optional discovery feeds do not establish conclusions about their contents.

Exclude only run receipts in `docs/evidence/convergence/`, disposable audit outputs in `docs/evidence/audit-runs/`, and the historical `docs/evidence/document-receipt.json`. They describe runs, not operating contracts. A file used operationally must be moved into the keyed closure; an exclusion cannot hide a governing control. These exclusions avoid a receipt changing the very key it attests. Product deficits remain recorded and block PRODUCT_RELEASE; they do not make a specification incomplete when faithfully captured with executable acceptance/disposition.

## Preflight and changed passes

Complete XY alternatives, current-practice retrieval, source reconciliation, portability and missing execution-contract repairs before the first zero-change pass. Preserve material findings and applied dispositions. Failed tests, missing relevant authority/capability, contradictions, untracked material inputs, unsupported assurance claims or missing lifecycle transitions block specification convergence. Cosmetic alternatives, duplicative mechanisms and unsupported speculative controls do not justify churn.

A reviewer must try to falsify the package using concrete examples. A checker's PASS proves only its tested structural/protocol properties. Coverage of full semantics requires actual review. If a pass discovers a material fix, apply it, run impacted checks, compute a new key and reset the consecutive count to zero. Do not amend this rubric merely to approve the candidate.

## Three consecutive complete reviews

Each pass covers all scope classes: intent/constraints; rules/content; both role journeys/state; architecture/toolchain; source/release integrity; test/evidence semantics; autonomous authority/task selection; interruption/concurrency/effects; privacy/security; offline/recovery/migration; UX/localization/accessibility/assets/rights; operations/support/maintenance/retirement; currentness/descendant inheritance; and claim/receipt boundaries.

1. **Forward requirements review:** reconstruct a new authorized executor's path from Y through discovery/specification to release and retirement. Check that every requirement/test/task has a source, action, owner role, dependency and observable gate. Challenge ambiguous budget, manual role handoffs, unrevealed information, pending educational acceptance and stalled M0. Use the contract checker and source/reference comparison evidence.
2. **Failure-first review:** trace backward from wrong award, lost save, unauthorized publish, forged green report, stale confirmation, interrupted remote write and premature disposal. Exercise synthetic negative inputs and semantic mutants. Check each scope class for missing prevention/detection/recovery and whether new controls would create worse burden or dependencies.
3. **Fresh-resume/release/retirement review:** treat chat context as unavailable. Verify the package contains its original sources, operating instructions and actual next work; use a different deterministic inspection (Python/standard library) for hashes, mapping/inventory and retained-original identity. Reconcile remote state. Walk a normal accepted release, later repair and actual retirement without claiming any happened. Inspect the entire scope, not only packaging.

For each pass save candidate key before/after, inspected scope, performed methods, concrete challenges, findings/dispositions, result and remaining limitations. Single-agent sequential self-review can supply distinct framings and tools but must not be called independent or cross-model assurance. Three command reruns alone never qualify. Freeze the final key only after all known material corrections; stop after the third passing same-key review unless genuinely new material evidence reopens it.

## Receipt and invalidation

Store exact manifest, pass records, executable check outputs, limitations and final outcome outside the keyed candidate. A receipt states SPECIFICATION CONVERGED only if all three actual reviews are zero-change, consecutive and same-key. It states neither that R01-R26 passed in the product nor that the game is complete. Any material candidate/policy/evaluator/evidence/environment change invalidates the receipt until reconciled. A later commit may change the bound HEAD even with equal working files; regenerate/review the affected identity basis rather than copying the old key claim.
